# 계산 방식

모든 숫자는 계산식과 입력값을 함께 남깁니다. 화면에서 값에 마우스를 올리면 어떻게 나왔는지 보입니다. **예시값**이라고 적힌 기본값은 형식 확인용이니 잰 값으로 바꾸세요.

## 계산 순서

```mermaid
flowchart LR
  A["설정<br/>규모·페르소나·하루 피크"] --> B["트래픽<br/>시간대별 RPS·1분 곡선"]
  B --> C["부하<br/>연결선을 따라 내려감"]
  C --> D["용량<br/>대수·사용률·p99·DB 연결"]
  C --> E["파이프라인<br/>큐 적체·자동 확장·배치"]
  D --> F["장애<br/>존·리전·백업"]
  D --> G["비용<br/>가격표"]
  E --> G
  D --> H["한계 사용자·성장"]
  D & E & F --> J{"판정"}
  J --> R["됨 · 조건부 · 판단 불가 · 안 됨"]
```

## 트래픽

| 무엇 | 어떻게 |
|---|---|
| 하루 트래픽 | 페르소나마다 접속 시각·횟수·시간을 무작위로 뽑아 하루를 만듦 (시드가 같으면 결과도 같음) |
| 이벤트 피크 | 평소 피크 × 이벤트 배수 |
| 데이터 주고받기 | 폴링 주기·모아 보내기가 요청 수를 바꿈 |
| 1분 곡선 | 같은 가정의 평균 곡선. 하루 양은 무작위 하루와 같게 맞춤 → 아래 그래프·큐 소비자·주기 배치에 씀 |
| 일시적 급증 (켰을 때) | 무작위 시각(시드 고정)에 1 → 높이 → 1로 오르내림. 겹쳐도 높이(최대 1.5배)를 넘지 않음 |

```
부하 ▲      급증(높이 1.2배, 10분)
     │        ╱╲
     │   ____╱  ╲____       ← 평소 곡선
     │  ╱              ╲
     └──────────────────────▶ 시각
```

> 급증은 1분 곡선(그래프·큐 소비자·주기 배치 1회 양·자동 확장 API 서버)에 들어갑니다. 필요 대수를 정하는 피크 RPS는 바꾸지 않습니다.
> 자동 확장을 켠 API 서버(backend·gateway, 주 서버 1대 DB가 아닌 주 항목에 `autoscale`이 있을 때)는 1분 곡선(급증 포함)으로 큐 소비자와 같은 하루 시뮬레이션을 돌려, 새 서버가 뜨기 전 도착이 떠 있는 대수의 처리량을 넘는 시간(분)과 가장 큰 사용률을 판정합니다. 1건 처리 시간 = 1000 / 대당 처리량, 최소 = max(최소 대수, 이중화), 최대 = `autoscale.max` 없으면 항목의 최대 대수(`autoscale.max`가 커도 항목의 최대 대수를 넘지 않음). 비용도 이 시뮬레이션의 시간대별 대수를 씁니다.

## 용량 · 지연 · 한계

| 값 | 계산 |
|---|---|
| 연결선 부하 | 보내는 노드 부하 × 호출 비율 (읽기·쓰기 구분, 캐시가 앞에 있으면 DB 읽기 × (1 − 적중률), 적중률 기본 0.8 **예시값**). 화면 와이어프레임 호출 → 인터페이스 명세 → 호출 비율 순으로 먼저 있는 것을 씀 |
| 인터페이스 명세 | 인터페이스마다 (모든·읽기·쓰기) 요청 × 횟수. 받는 쪽 읽기·쓰기는 명세의 구분대로. 파일·전문은 쓰기, 크기는 레코드 길이(고정장 = Σ 필드 길이 + 줄바꿈, 가변장 = Σ 값 + 구분자 + 줄바꿈). 고정장 길이가 빠진 필드는 형식별 **예시** 크기로 어림(고정장은 평균 크기를 쓰지 않음). 가변장 문자열은 평균 크기가 없으면 32바이트로 보고 인코딩(EUC-KR·UTF-8)은 크기에 넣지 않음 |
| 테이블 행 크기 | Σ 값 크기 + 저장 시스템의 행·컬럼 오버헤드. 고정장 테이블은 PostgreSQL·MySQL에서 문자열을 최대 길이로 셈 (SQLite는 실제 길이). 바이너리는 어디서나 실제 길이로 세서 MySQL BINARY(n)은 조금 적게 나올 수 있음 |
| 필요 대수 | ceil(부하 / (대당 처리량 × 목표 사용률)), 최소·최대 대수로 자름 |
| 대당 처리량 | 업계 기준값 → 사양(vCPU·메모리)으로 보정 → 실측이 있으면 실측. 처리 시간(동시 처리 수·평균 처리 ms)을 넣으면 min(그 값, 동시 처리 수 × 1000 / 평균 처리 ms) — p99와 같은 한계 |
| 주 서버 1대 DB | 쓰기는 주 서버가 모두, 읽기 복제본이 있으면 읽기만 나눔 |
| DB 연결 수 | Σ 부르는 노드 대수 × 연결 풀(기본 10). 연결 풀러가 있으면 풀러 크기까지 |
| 대역폭·동시 연결 | 진입 서버 노드(화면에서 오는 연결선이 있는 gateway·backend)만. 대역폭은 노드 전체 응답(NIC가 다 실어 나름) = 그 노드 부하 × 평균 응답 크기(하루 송신 / 하루 요청) × 8 / 1000 Mbps, 연결은 화면에서 직접 오는 몫 = 피크 동시 접속 × 화면에서 그 노드로 직접 오는 흐름 / 진입 서버 노드 직접 흐름 합(다른 진입 서버가 넘긴 부하는 세지 않음). 한도 = 대당 한도(노드 `net.max_mbps`·`net.max_connections`, 비면 주 항목 기준값 `thresholds.mbps`·`thresholds.client_connections` — 게이트웨이 6종 1,000 Mbps·10,000 연결 **예시값**) × 그 피크의 대수. 대수는 RPS·대역폭·연결 중 가장 많이 필요한 것(같은 목표 사용률, 사용률 표시는 RPS 기준; 자동 확장 API 서버의 하루 시뮬레이션은 RPS 기준)이라 최대 대수에 막혔을 때만 넘음. 한도가 없으면 비교하지 않음. 부하에 비례하므로 한계 사용자 탐색에도 넣음 |
| p99 | 대기열 모형(Erlang C, 서버 수 × 동시 처리 수가 1000을 넘으면 Halfin–Whitt 근사). 경로 p99는 동기 경로를 따라 더함. 경로가 500개를 넘으면 앞쪽 500개만 계산하고 알림 |
| 한계 사용자 | 이벤트 피크에서 "안 됨"이 되기 직전의 사용자 수. 가장 먼저 닿는 노드 = 첫 병목. 자동 확장 넘침은 한계 탐색에 넣지 않음(사용자 수에 단조롭지 않음) |

## 데이터 파이프라인

```mermaid
flowchart LR
  P["보내는 노드"] -->|메시지| Q[("큐<br/>파티션 N")]
  Q -->|"처리량 = min(대수 × 동시 처리, 파티션) × 1000 / 처리 ms"| C["소비자"]
  Q -. "도착 > 처리량이면 적체" .-> L["지연 = 적체 / 처리량 + 처리 시간"]
```

| 소비자 | 계산 |
|---|---|
| 고정 대수 | 하루를 30초 칸으로 돌림. 도착은 설정의 계산 단위(1·5·15·60분, 기본 60분)마다 평균 |
| 자동 확장 (KEDA처럼) | 1분 곡선으로 하루를 30초 칸으로 돌림. 아래 그림처럼 대수를 바꿈 |
| 주기 배치 | 1회 실행 = 하루 중 주기 길이 창에 들어온 가장 많은 양 / 처리량 (실행 창 안에 끝나야 함; 주기가 하루 이상이면 하루 양 × 주기 / 1440), 반영까지 최대 = 주기 + 1회 실행 |

자동 확장 한 번의 흐름:

```mermaid
sequenceDiagram
  participant T as 트래픽
  participant K as 자동 확장
  participant C as 소비자
  T->>K: 도착이 늘어남
  Note over K: 확인 주기(기본 30초)마다<br/>필요 대수 = ceil(도착 × 처리 시간 / (동시 처리 × 목표 사용률))
  K->>C: 늘림
  Note over C: 뜨는 시간(기본 30초, 예시값) 동안은<br/>이전 대수로 받아 적체가 생김
  T->>K: 몰림이 끝남
  Note over K: 줄이기 전 기다림(기본 300초) 동안<br/>필요했던 가장 큰 대수 아래로는 안 줄임
  K->>C: 줄임
```

비용은 시간대별 평균 대수, DB 연결 수는 가장 많을 때 대수(API 자동 확장 노드는 피크 기준 대수)로 셉니다.

## 장애

늘 떠 있는 대수 = max(이중화, 최소 대수), 패턴의 최대 대수 이하. 가용성·단일 장애점·존 장애가 이 대수를 씁니다.

| 장애 | 멈추는 것 | 남는 사용률·시간 | 기본값 (**예시값**) |
|---|---|---|---|
| 존 하나 | 존이 1개뿐인 노드 | 남은 서버 사용률 = 지금 × 대수 / 남은 대수 (잃는 대수 = ceil(대수 / 존 수)). 대수 = max(계산 대수, 늘 떠 있는 대수) | 주 서버 DB 넘기기 60초 |
| 리전 하나 | 다른 리전 복사본이 없는 노드 → 그 노드에 동기로 닿는 화면 | 대기 복사본으로 넘긴 직후 사용률 = 지금 × 대수 / 대기 대수 | 넘기기: 같이 받기 60초, 대기 900초 |
| 캐시 장애 | 캐시 노드 전부 (읽기가 모두 DB로) | 캐시 적중률을 0으로 두고 부하를 다시 계산해 늘어나는 노드(보통 DB)의 사용률 = 캐시 없을 때 부하 / (대수 × 대당 처리량), 대수 그대로 (주 서버 1대 DB는 읽기 복제본이 있으면 max(쓰기 / 대당 처리량, 읽기 / (복제본 수 × 대당 처리량)), 없으면 부하 / 대당 처리량) | 적중률 0.8 → DB 읽기 5배 |
| 데이터 손상 | — | RPO = 백업 주기·시점 복구·복제 지연 중 짧은 것<br/>RTO = 새 서버 준비 + 데이터 크기 / 되살리는 속도 | 시점 복구 5분, 복제 지연 5초, 준비 10분, 100MB/초 |

## 비용

한 달 = 730시간(클라우드 가격표 기준). 하루 값은 × 730/24로 한 달로 바꿉니다. 월 중단 시간도 730시간 기준입니다.

```mermaid
flowchart LR
  N["노드"] --> P1["대수 × 시간<br/>(시간대별 대수)"]
  N --> P2["사용량<br/>(요청·연산 시간·스캔량)"]
  N --> P3["월 정액"]
  S["프로젝트"] --> P4["저장 · 송신 · 리전 간 전송<br/>· 존 간 전송"]
  N --> P6["로그 저장<br/>(보관 중인 양)"]
  R["리전 복사본"] --> P5["같은 대수 또는 대기 대수<br/>+ 복사본 저장 + 복제 전송"]
  P1 & P2 & P3 & P4 & P5 & P6 --> T["월 합계"]
```

연결선의 전송량은 인터페이스 명세가 있으면 Σ 월 호출 × (요청 + 응답 크기), 없으면 사용자 응답 평균 크기로 어림합니다. 리전이 다른 연결선은 이 전송량 전부를 **리전 간 전송**으로 셉니다.

| 줄 | 대상 | 수량 | 상품 (설정 › 비용 기준) |
|---|---|---|---|
| 존 간 전송 | 같은 리전의 서버 노드 사이 연결선(화면·외부·사용자 기기 제외, 양쪽 주 항목이 직접 운영 `provisioned`일 때만: SQS·DynamoDB 같은 리전 단위 관리형은 AZ 간 요금이 없고 Neon·Turso는 다른 업체 청구서), 두 노드 중 큰 존 수 z가 2 이상 | 전송량 × (1 − 1/z) GB. 단가는 양방향 합(AWS는 보내는 쪽 0.01 + 받는 쪽 0.01 = 0.02). 두 노드가 같은 존들에 고르게 퍼져 있고 호출이 무작위로 간다고 봄(존 친화 라우팅은 반영 안 함) | 존 간 전송 (단위 `gb_interzone`) |
| 로그 저장 | 요청당 로그(KB)를 넣은 서버 노드 | 보관 중인 양 = 하루 로그 GB(월 요청 × 요청당 KB ÷ 730/24일) × 보관 일수(없으면 30) GB·월. 수집 요금은 상품마다 달라 넣지 않음 | 로그 저장 (단위 `gb_month`) |

상품을 고르지 않으면 그 줄은 계산하지 않습니다. 가격이 없는 상품·리전은 0원으로 채우지 않고 **가격 없음**으로 알립니다.

## 판정

```mermaid
flowchart TD
  S["항목의 조건 · 노드 공통 규칙"] --> N{"평소 피크에서<br/>걸림?"}
  N -- 예 --> F["안 됨"]
  N -- 아니오 --> E{"이벤트 피크에서만<br/>걸림?"}
  E -- 예 --> C["조건부"]
  E -- 아니오 --> M{"값이 없음?"}
  M -- 예 --> U["판단 불가"]
  M -- 아니오 --> O["됨"]
```

| 노드 공통 규칙 | 평소 | 이벤트에서만 |
|---|---|---|
| 사용률 100% 초과 | 안 됨 | 안 됨 |
| 큐 지연 > 허용, 배치 실행 > 실행 창 | 안 됨 | 조건부 |
| 자동 확장 API 서버가 넘친 시간 > 0분 (`autoscale_over_min`) | 안 됨 | 조건부 |
| 응답 대역폭·동시 연결 > 대수 × 대당 한도 (`peak_mbps > max_mbps_total`, `concurrent_conns > max_conns_total`) | 안 됨 | 조건부 |
| 장애 목표: 화면이 멈춤 / 반영만 늦음 | 안 됨 / 조건부 | |
| 장애 목표: 장애 직후 넘침 | 조건부 (자동 확장이 채움) | |
| 장애 목표: 캐시가 멈추면 사용률 100% 초과 (`cache_util`, 장애 목표가 있으면 견딜 장애 종류와 상관없이) | 조건부 | 조건부 |
| 장애 목표: RTO·RPO 초과 | 안 됨 | |

판정 순위: 됨 < 조건부 < 판단 불가 < 안 됨

## 네트워크 · 보안

노드·연결선의 보안 값과 구조로 점검합니다. 항목 판정과 따로 내며, 노드 판정 배지는 보안 ❌만 바꿉니다. 설계 값으로 하는 점검이라 실제 보안 그룹·인증서·침투 시험을 대신하지 않습니다.

| 점검 | 단계 |
|---|---|
| DB·캐시·큐·분석 노드가 인터넷 공개 | ❌ |
| 인터넷을 지나는 연결선이 암호화 없음 | ❌ |
| 개인정보 저장 노드의 저장 암호화 끔 | ❌ |
| 인터넷 공개 게이트웨이·백엔드에 WAF·속도 제한 끔 (token_bucket·kong 항목이나 한도 값 `rate_limit_rpm`이 있으면 속도 제한 충족) | ⚠️ |

인터넷 공개 노드마다 설계서에 위협 점검표(STRIDE: 위장·변조·부인·정보 노출·서비스 거부·권한 상승)를 붙이고, 이미 정한 값은 괄호로 보여 줍니다. 줄마다 상태를 붙입니다: ✅ 값으로 막혀 있음, ⚠️ 확인 필요(값이 끔이거나 인증 없는 인터페이스가 있음), 미정(값이 비어 판단 못 함). 위장은 인증 없는 인터페이스·인증 방식·토큰 수명(위 점검과 같은 기준)·MFA(개인정보나 고객 구분 컬럼이 있는데 없음이면 ⚠️), 권한 상승은 권한 모델·관리자 분리(비면 미정)·테넌트 분리(고객 구분 컬럼이 있는 저장 노드가 나누지 않음이면 ⚠️)로 정하고, 부인은 프로젝트에 개인정보 노드가 없으면 해당 없음(✅)입니다.

외부 서비스 노드의 판정 변수 `has_timeout`(동기 외부 호출 항목이 씀)은 노드 vars에 없으면 자동으로 채웁니다: 들어오는 동기 연결선 모두에 타임아웃이 있으면 true, 하나라도 비면 false, 동기 연결선이 없으면 넣지 않습니다. 노드 vars에 적은 값이 우선합니다.

## 성장 · 법령

- **성장:** 월 성장률 또는 유입 모형으로 달마다 사용자 수를 구합니다. 노드마다 한계에 닿는 달과 준비를 시작할 달, 달별 비용, 파티션 없는 테이블이 메모리를 넘는 달을 보여 줍니다.
- **법령:** 개인정보를 두는 노드의 리전·데이터 주체 나라로 한국·일본 법령의 "확인할 조문"을 표시합니다. 개인정보 노드에는 파기 조문(개인정보 보호법 제21조, 個人情報保護法 第22条)도 붙습니다. 법률 검토를 대신하지 않습니다.
